# Defendra — техническое задание

Defendra — локальная утилита для Ubuntu VDS. Человек без опыта в безопасности ставит её на свежий сервер, запускает одну команду, и сервер приводится к безопасной базовой конфигурации. Дальше Defendra сама следит, что эту конфигурацию не разъехало, и говорит простым языком, если что-то не так.

Целевой пользователь: купил VDS, получил IP и пароль root, не хочет разбираться в SSH, UFW и fail2ban, боится взлома и «какого-то DDoS». Не админ. Экраны, ошибки и путь «от письма хостера до зелёного статуса» описаны в [`UX.md`](UX.md). Если этот файл и UX.md спорят про текст на экране — прав UX.md.

## 1. Честное обещание

Defendra закрывает типичные дыры свежего VDS, через которые чаще всего взламывают такие серверы:

- подбор пароля SSH (самая частая атака на новый VDS);
- вход под `root`;
- открытый Redis/Postgres/MySQL в интернет;
- отсутствие файрвола;
- отсутствие автообновлений безопасности;
- простые сетевые флуды на сам сервер (SYN, brute-force).

Defendra **не** делает сервер неуязвимым и **не** останавливает объёмный DDoS на канал (гигабиты мусора до сервера). Это задача хостера и Cloudflare. В интерфейсе это сказано прямо, без мелкого шрифта.

После `defendra protect` пользователь должен мочь уйти и не думать о базовой гигиене. Если безопасность снова ослабнет — Defendra сама напишет об этом при входе по SSH и в `defendra status`.

## 2. Принципы

1. Одна главная команда: `sudo defendra protect`. Без аргументов `defendra` показывает меню, не список флагов.
2. Говорить по-русски, короткими предложениями, без жаргона. Если нужен термин — сразу перевод в скобках. В интерфейсе запрещены слова: UFW, fail2ban, sshd, jail, CIS, finding, sysctl.
3. Спрашивать только то, без чего можно потерять доступ. Один вопрос за раз. Enter = да. Не `Y/n`.
4. Помечать, где выполнять команду: «на своём компьютере» или «на сервере».
5. Сначала гарантировать следующий вход, потом закрывать дыры.
6. Консоль хостера (VNC/KVM) — запасной вход. Пароль учётной записи `root` не блокируем: выключаем только вход root **по SSH**.
7. Повторный запуск безопасен. Ctrl+C посредине → «запустите protect ещё раз».
8. Каждое изменение пишется в журнал и имеет откат.
9. Никакой телеметрии, никаких звонков «домой».
10. Не обещать защиту от того, чего локальная программа не умеет.
11. Ставится копипастом двух команд. Без Go, git clone и «собери из исходников».
12. Долгое apt не молчит: «шаг 2 из 9» и человеческое название шага.
13. Найденную панель управления (FastPanel, ISPmanager и т.п.) не закрывать молча: спросить, Enter = оставить порт. Саму панель не настраиваем.

## 3. Платформа

| | |
|---|---|
| ОС | Ubuntu Server 22.04 LTS, 24.04 LTS и 26.04 LTS |
| Откуда ставят | типичный VDS: root + пароль или root + ключ из панели хостера |
| Архитектура | amd64, желательно arm64 |
| Язык реализации | Go, один статический бинарник |
| Установка | готовый `.deb` с GitHub Releases (или зеркала). На сервере не нужен компилятор |
| Права | все команды, которые меняют систему — через `sudo` / root |
| Сеть утилиты | не ходит в интернет, кроме `apt` когда ставит пакеты защиты |

Не поддерживаем в v1: Debian, CentOS, Docker Swarm, Kubernetes. Панели ISPmanager/Fastpanel **не настраиваем**, но их порты не закрываем молча, см. шаг 3 и UX.md.

### 3.1 Как ставят (скачать, сверить, поставить)

Новичок не собирает проект. В README, help и на странице релиза один и тот же копипаст. Сверяют файл до установки:

```text
curl -fsSL https://github.com/johnkaine45/defendra/releases/latest/download/defendra_amd64.deb -o defendra_amd64.deb
curl -fsSL https://github.com/johnkaine45/defendra/releases/latest/download/defendra_amd64.deb.sha256 -o defendra_amd64.deb.sha256
sha256sum -c defendra_amd64.deb.sha256
sudo apt install ./defendra_amd64.deb
```

Потом сразу:

```text
sudo defendra protect
```

Допустимо: человек скачал `.deb` в панели браузера, залил на сервер и сделал только `sudo apt install ./defendra.deb`.

Недопустимо как основной путь: `git clone`, `go install`, `make`, pip, snap.

Файл `.deb` сопровождается checksum (SHA256) на той же странице релиза. Имя для копипаста — `defendra_amd64.deb` (latest), плюс версия `defendra_0.1.23_amd64.deb`. README и `defendra help` сверяют файл через `sha256sum -c` до `apt install`. `protect` эти URL сам не качает. Обновление уже установленной утилиты — `sudo defendra update`: HTTPS на GitHub, сверка SHA256, `apt install` локального файла. Старую версию не ставит.

## 4. Как это выглядит для пользователя

Экраны, точные фразы, меню, FAQ и каталог ошибок — [`UX.md`](UX.md). Ниже — только поведение. Если макет в этом разделе расходится с UX.md, верна UX.md.

### 4.1 Первый запуск на новом VDS

После установки из §3.1, **на сервере**:

```text
sudo defendra protect
```

Прогресс: `Defendra • шаг 2 из 9` и человеческое имя шага, без имён пакетов.

- Ключ уже есть у root — копируем `admin`, короткий план, Enter = продолжить. Тексты: UX.md §5.1.
- Ключа нет — не выключаем пароль. Сначала спросить Windows / Mac / «вставлю ключ» / «пока без ключа». Вставку ключа валидировать (отказ на PRIVATE KEY). Тексты: UX.md §5.2–5.3.
- Найдена панель — вопрос, Enter = открыть её порт. UX.md §5.4.
- Ключ с сервера не генерируем.

Пока ключа нет — частичная защита, статус «не полностью».

### 4.1.1 Ритуал второго окна и два пароля

Если SSH закрыли — сначала «ЭТО ОКНО НЕ ЗАКРЫВАЙТЕ» и вход `ssh admin@IP` со **своего компьютера**, затем таблица двух паролей (SSH без пароля / sudo от Defendra / root из письма хостера для консоли). Точные тексты: UX.md §5.6 и §6.

`how-to-login` печатает то же. Сессия жива: reload, не restart.

### 4.2 После настройки

`sudo defendra status` — три состояния словами: порядок / не полностью / опасно. Одна причина, одна команда. Макеты: UX.md §7. Никогда не советовать выключить файрвол.

`defendra` без аргументов — меню. `defendra help` — FAQ «не вхожу».

### 4.3 Команды, которые существуют в продукте

| Команда | Зачем обычному человеку |
|---|---|
| `defendra` | Меню: что делать дальше. Не список флагов. |
| `defendra help` | FAQ: не вхожу, какой пароль, сайт, консоль хостера. |
| `sudo defendra protect` | Настроить или дожать защиту. Главная команда. |
| `sudo defendra status` | Всё ли в порядке, простыми словами. |
| `sudo defendra undo` | Откатить последний `protect`. |
| `sudo defendra allow-site` | Открыть сайту 80 и 443, не выключая защиту. |
| `sudo defendra update` | Скачать новую версию с GitHub, сверить SHA256, поставить `.deb`. Не откатывает на старую. |
| `defendra how-to-login` | Как заходить, два пароля, ритуал второго окна, консоль хостера. |

Команды не для главного экрана: `scan`, `explain`, `--dry-run`, `--yes`, `--format json`, `version`. В меню новичка их нет.

Скрытые/служебные:

| Команда | Зачем |
|---|---|
| `sudo defendra protect --dry-run` | Показать план, ничего не менять. |
| `sudo defendra protect --yes` | Без вопроса, для скриптов. Enter в обычном режиме = да. Если нет ключа — всё равно отказ на шаг «закрыть пароль». |
| `sudo defendra allow-site --dry-run` | Показать правила UFW, ничего не менять. |
| `sudo defendra scan --format json` | Для нас и для автоматизации, не для главного экрана. |
| `sudo defendra version` | Версия. |

Не делаем в v1: `fix SSH-001` по отдельным ID как основной UX, веб-кабинет, Telegram-бот, HTML-отчёт.

## 5. Что именно настраивает `protect`

Профиль по умолчанию: **fresh-vds** — один админ, один сервер, возможно сайт, базы только локально.

Порядок шагов фиксирован. Менять его нельзя: от него зависит, не выкинем ли мы человека из SSH.

### Шаг 0. Предусловия

- Ubuntu 22.04/24.04/26.04, иначе стоп текстом из UX.md.
- Запуск от root. Без sudo — подсказать точную команду, не `permission denied`.
- Похоже на Ubuntu Desktop, не на VDS — предупреждение, по умолчанию отказ.
- Есть активная SSH-сессия или локальная консоль. Если SSH — запомнить порт, адрес и не банить этот IP в fail2ban.
- Снять факты: пользователи, `authorized_keys`, слушающие порты IPv4 **и** IPv6, UFW, пакеты, sshd_config, известные панели (FastPanel, ISPmanager, Hestia, Webmin, Plesk, CyberPanel, Cockpit).

### Шаг 1. Админ вместо повседневного root

- Пользователь по умолчанию: `admin` (флаг `--user`).
- Группа `sudo`.
- Домашний каталог, `~/.ssh/authorized_keys` mode `600`, `.ssh` mode `700`.
- Если у `root` уже были ключи — копируются `admin`.
- Пароль пользователя: случайный, показывается **один раз**, нужен для `sudo` на сервере. Печатается крупно + пишется в `/var/lib/defendra/first-login.txt` (права `600`). Если `admin` уже был, а файла ещё нет — задаём новый пароль один раз на первом protect. Повторно не крутим. Если после смены пароля protect оборвался (apt, фильтр, sudoers) — коробку всё равно печатаем. В `how-to-login` напоминание: «сохраните пароль sudo, через SSH он не спрашивается».
- Passwordless sudo в v1 **не** включаем: потеря ноутбука не должна давать полный root без пароля. Для человека это объясняется одной строкой.
- Учётную запись `root` **не** блокируем (`passwd -l`, `usermod -L`, удаление пароля). Иначе консоль хостера перестанет пускать, и `undo` будет нечем вызвать. Пароль root из письма хостера остаётся для VNC/KVM.

### Шаг 2. Пакеты защиты

Через `apt` (единственные легитимные обращения в сеть):

- `ufw`
- `fail2ban`
- `unattended-upgrades`

Если `apt` недоступен — шаг падает, предыдущее не откатывается автоматически (пользователь уже создан — это ок), статус жёлтый.

### Шаг 3. Файрвол — сначала дырки для себя, потом замок

1. Сначала `allow` уже слушающих публичных TCP и UDP (сайт, Docker, VPN, SSH; панель — только если на вопрос ответили да). Потом `default deny incoming`, `default allow outgoing`. Не наоборот — иначе прод на секунды теряет порты.
2. Allow текущего SSH-порта TCP на IPv4 и IPv6.
3. Если уже слушают 80/443 (nginx, caddy, apache, traefik) — allow 80 и 443.
4. Иначе 80/443 **не** открываем «на всякий случай». Сайт, который поставят завтра, открывают командой `defendra allow-site`, а не выключением UFW.
5. Если найдена панель управления — один вопрос, Enter = allow её порта (IPv4 и IPv6). Ответ «нет» — порт панели не оставляем в leftover и снимаем его allow, если он уже был. Это не молча: человек ответил.
6. Только после правил — `ufw enable`.
7. Если `ufw enable` не подтвердил active — стоп, не идём закрывать SSH.
8. На Ubuntu 24.04/26.04 порт 22 часто слушает `ssh.socket`, а `ssh.service` поднимается по подключению. После включения фильтра сокет снова `start`, иначе новые входы получают «Connection refused», хотя текущая сессия ещё жива. `apt` не должен перезапускать SSH через needrestart. Если SSH-клиент отвалился посредине, `protect` не умирает от SIGHUP и доводит шаг до конца.

Произвольные порты (8888 «на всякий случай», 10000 без Webmin) Defendra сама не открывает.

### Шаг 4. fail2ban

- Jail `sshd` включён.
- Ban после 5 неудачных попыток за 10 минут, бан 1 час.
- Не банить 127.0.0.1 и текущий IP сессии, если он виден из `SSH_CONNECTION`.
- В интерфейсе: «защита от подбора пароля», не имя пакета.
- Если служба не стала active — SSH-пароль не закрываем, экран не пишет «готово».

### Шаг 5. Автообновления

- `unattended-upgrades` только для `-security`.
- Авторебут по умолчанию **выключен** (на VDS с сайтом внезапный ребут хуже, чем отложенный патч ядра). В status: «нужен перезапуск» если Ubuntu так сказала.

### Шаг 6. Базы не торчат в интернет

Если процесс слушает `0.0.0.0` или `::` на портах 5432, 3306, 6379, 27017, 9200, 2375:

- для **хостовой** службы (профиль fresh-vds) Defendra переводит listen на `127.0.0.1` (Redis, Postgres, MySQL, Mongo, Elasticsearch). Перезапуск — только после вопроса. `--yes` пишет файл и печатает, что с улицы ещё открыто, пока не сделают restart;
- Docker `-p 0.0.0.0` базу не трогает: статус красный, контейнер жив, на экране прямо сказано, что фильтр это не закроет;
- если в MySQL/MariaDB нет живой строки `bind-address` — не дописываем её в чужой client.cnf. Пишем свой drop-in `zz-defendra.cnf` в каталог, который Ubuntu уже подключает;
- если не умеет пропатчить уверенно — не трогает файл, включает UFW deny на этот порт снаружи (уже default deny) и пишет: «слушает всех, фильтр с улицы не пускает; лучше слушать только на сервере».

Не закрываем и не переписываем то, что уже слушает только localhost.

### Шаг 7. Сетевые sysctl (мелкий флуд, не «анти-DDoS продукт»)

Минимальный набор, который Ubuntu переживёт:

- `net.ipv4.tcp_syncookies=1`
- `net.ipv4.conf.all.rp_filter=2` (мягкий: Docker и асимметрия маршрутов на VDS не ломаются)
- `net.ipv4.conf.all.accept_redirects=0`
- `net.ipv4.conf.all.send_redirects=0`
- `net.ipv4.icmp_echo_ignore_broadcasts=1`
- `net.ipv4.tcp_max_syn_backlog` поднять умеренно

Пишем в `/etc/sysctl.d/99-defendra.conf`, затем `sysctl --system`. Не ставим сторонние «DDoS Deflate» скрипты.

### Шаг 8. SSH закрывается последним

Только если gate пройден: у `admin` непустой `authorized_keys`, ключ не world-writable, `sshd -t` на копии конфига проходит.

Тогда в drop-in:

- `PermitRootLogin no` — только SSH. Это не `passwd -l root`.
- `PasswordAuthentication no`
- `KbdInteractiveAuthentication no`
- `PubkeyAuthentication yes`
- `PermitEmptyPasswords no`
- `X11Forwarding no`
- `MaxAuthTries 3`
- `AllowUsers admin` (или выбранное имя)

Порт SSH **не меняем**. Смена порта ломает вход из панели и почти не спасает.

Правка через drop-in `/etc/ssh/sshd_config.d/00-defendra.conf` (OpenSSH first-wins), не ломая cloud-init хостера. Потом `sshd -t`, затем `reload` того unit, который сейчас active (`ssh` или `sshd`), не `restart`. На 26.04 после reload снова `start ssh.socket`. После reload читаем `sshd -T`: пароль/root и `AllowUsers` должны совпасть с задуманным, иначе откат drop-in. `sshd -T -C` (localhost, IP сессии, `user=`) — если ни один вызов не ответил, lock не считаем проверенным и откатываем. Тихий повторный protect пересобирает drop-in, если в `AllowUsers` нет нового пользователя с ключом. Текущая сессия должна выжить, чтобы сработал ритуал второго окна (§4.1.1).

Если gate не пройден — этот шаг пропускается, статус жёлтый, пароль SSH жив, fail2ban уже работает.

После успешного шага — обязательно печать ритуала второго окна. Без этого шага `protect` не считается законченным для UX, даже если конфиг уже записан.

### Шаг 9. Самопроверка и памятка

- `sshd` active, UFW active, fail2ban active.
- Порт SSH allowed.
- Печать `how-to-login` (включая ритуал второго окна, если SSH закрыли, и консоль хостера).
- Состояние в `/var/lib/defendra/state.json`.
- Systemd timer `defendra-watch`: раз в день `defendra scan --quiet` и обновление MOTD.

### Шаг 10. MOTD

При каждом SSH-входе короткая строка:

- зелёный: `Defendra: сервер в порядке`
- жёлтый: `Defendra: защита неполная — sudo defendra status`
- красный: `Defendra: появился открытый порт 6379 — sudo defendra status`

## 6. Что Defendra говорит про DDoS

В `protect`, `status` и `explain` один и тот же смысл:

> Большую DDoS-атаку (когда забивают интернет-канал) программа на сервере не остановит. Включите защиту в панели VDS. Если есть сайт — поставьте Cloudflare. Defendra закрывает другой класс проблем: взлом через SSH, открытые базы, сканирование портов и мелкий флуд.

Локально делаем только то, что реально работает на машине: файрвол, fail2ban, syn-cookies. Не рисуем «щит 99%».

## 7. Постоянный надзор

После `protect` Defendra не «закончилась».

Раз в день timer:

1. Снимает факты (порты, sshd, ufw, пользователи, fail2ban).
2. Сравнивает с профилем fresh-vds и с последним известным хорошим состоянием.
3. Если появился новый слушающий `0.0.0.0` порт, выключился UFW, снова включился пароль SSH, появился второй UID 0 — статус красный, MOTD, запись в `/var/log/defendra/watch.log`.
4. Сама ничего не чинит по таймеру. Чинит только человек командой `protect` (или позже точечно). Молчаливый ночной apply — способ сломать прод.

`protect` при повторном вызове дожимает то, что ещё жёлтое/красное, теми же шагами и теми же gates.

## 7.1 Открыть сайт, не снимая файрвол

Сайт часто ставят на второй день. Если 80/443 закрыты, новичок в панике делает `ufw disable` и возвращает все дыры.

```text
sudo defendra allow-site
```

Поведение:

1. UFW должен быть включён (обычно после `protect`). Если выключен — не «тихо enable без SSH allow». Стоп: «сначала `sudo defendra protect`, потом открывайте сайт».
2. Allow `80/tcp` и `443/tcp` на IPv4 и IPv6. SSH-правило не трогаем.
3. UFW остаётся active. Никаких `ufw disable`.
4. Идемпотентно: повторный вызов говорит, что уже открыто, exit 0.
5. `--dry-run` печатает правила, диск не меняет.
6. В `state.json` флаг `site_allowed: true`. Watch не считает 80/443 «неожиданным портом», даже если nginx ещё не слушает.
7. Если nginx уже слушает, а 80/443 закрыты — `status` жёлтый: «сайт запущен, файрвол его не пускает. Выполните sudo defendra allow-site».

Не открываем произвольные порты (`allow 8080`) в v1 — слишком легко выставить Redis.

## 8. Модель находки (внутренний контракт)

Для человека — фразы. Для программы и `scan --format json` — стабильные ID.

```json
{
  "id": "SSH-PASSWORD",
  "title": "Вход по паролю ещё включён",
  "severity": "high",
  "status": "fail",
  "plain": "Сейчас к серверу можно подобрать пароль. Нужен ваш SSH-ключ, потом Defendra выключит пароль.",
  "fix": "protect",
  "automatic": true,
  "gates": ["admin_has_ssh_key"]
}
```

| Поле | Смысл |
|---|---|
| `id` | Стабильный, не переиспользуем |
| `plain` | Одно-два предложения, русский, без CIS |
| `severity` | `critical` / `high` / `medium` / `low` / `info` |
| `status` | `pass` / `fail` / `warn` / `info` / `error` / `skipped` |
| `fix` | `protect` / `allow-site` / `none` |
| `automatic` | умеет ли `protect` это закрыть сам |
| `gates` | что должно быть правдой перед apply |

Severity для человека в status схлопывается в: защищён / не полностью / не защищён.

### Каталог v1 (обязательный)

| ID | Когда fail | `protect` чинит? |
|---|---|---|
| `SSH-ROOT-LOGIN` | root может войти по SSH | да, после ключа admin |
| `SSH-PASSWORD` | парольная аутентификация | да, после ключа admin |
| `SSH-NO-KEY` | ни у кого из sudo нет authorized_keys | нет, ждёт вставку ключа |
| `SSH-EMPTY-PASS` | пустые пароли разрешены | да |
| `FW-DISABLED` | UFW не active | да |
| `FW-SSH-MISSING` | UFW on, SSH-порт не allowed | да (сначала allow) |
| `FW-WEB-BLOCKED` | веб-сервер слушает 80/443, UFW их не пускает | нет: `defendra allow-site` |
| `NET-DB-EXPOSED` | postgres/mysql/redis/mongo/ES/docker API на 0.0.0.0/`::` | хост: localhost; Docker `-p`: нет, только красный статус |

## 9. Откат

`sudo defendra undo` откатывает **последний успешный protect** целиком:

- возвращает файлы из snapshot (`sshd` drop-in, sysctl, `ufw` rules и `ufw.conf`, fail2ban jail, sudoers.d если создавали);
- после отката reload SSH; фильтр: если в снимке он был выключен — выключаем, иначе `ufw reload`, чтобы живые правила совпали с файлами. Если в старом снимке нет `ufw.conf` — правила фильтра не откатываем, чтобы не закрыть SSH после reboot;
- удаляет файлы, которые Defendra сама создала и которых не было до protect (`00-defendra.conf` и другие свои drop-in). Живые `sshd_config`, `ufw.conf` и правила фильтра не удаляет, даже если копия в снимке пропала;
- не удаляет пользователя `admin` (удаление admin может закрыть единственный вход);
- не обещает откат `apt install`;
- после отката снова `sshd -t` и reload.

Если человек выключил пароль, потерял ключ и зовёт `undo` с KVM-консоли хостера — undo должен вернуть предыдущий sshd. Это основной сценарий спасения. Он работает только если пароль `root` для консоли не блокировали.

В `how-to-login` этот путь написан теми же словами, что в ритуале второго окна.

Пока undo не вызывали, в `/var/lib/defendra/backups/last/` лежит snapshot. Новый protect сдвигает его в `backups/archive/<timestamp>/` (храним 5 последних).

## 10. Хранение

```
/usr/bin/defendra
/etc/defendra/profile.json          # имя пользователя, ssh-порт на момент protect
/var/lib/defendra/
  state.json                      # прошёл ли protect, какие шаги, how-to-login, site_allowed
  summary.json                    # копия state, 0640
  first-login.txt                 # пароль sudo admin, 0600, после прочтения можно удалить
  scans/<timestamp>.json
  backups/last/
  backups/archive/
  apply.lock
/var/log/defendra/
  audit.log                       # команды и результаты
  watch.log
/etc/ssh/sshd_config.d/00-defendra.conf
/etc/sysctl.d/99-defendra.conf
/etc/fail2ban/jail.d/defendra.conf
/etc/update-motd.d/99-defendra
/etc/systemd/system/defendra-watch.timer
```

Владелец root. Каталог `/var/lib/defendra` — `0750` и группа админа, чтобы `defendra` / `how-to-login` без sudo видели статус. Секреты `0600`, `state.json` `0640`. Чужие в каталог не заходят.

Audit log: время, команда, шаг, ok/fail, путь backup. Без ключей и паролей.

## 11. CLI-контракт для реализации

Exit codes:

| Код | Когда |
|---|---|
| 0 | status зелёный; protect/undo/allow-site/dry-run успех; тихий повторный protect только если уровень «порядок» |
| 1 | status жёлтый или красный (для cron/watch); тихий protect, если уровень не зелёный |
| 2 | ошибка: не Ubuntu, нет root, сломан sshd, lock, apt fail, allow-site без активного UFW |

`--format json` — только stdout. Вопросы, прогресс и ритуал второго окна — stderr (чтобы JSON не ломать) **кроме** обычного text-режима, где ритуал идёт в stdout как главная памятка.

Без TTY `protect` требует `--yes` и всё равно не закроет SSH без ключа. Ритуал второго окна в `--yes` всё равно печатается.

`--dry-run` не задаёт вопросов и не читает stdin: только печатает план. Иначе в скрипте следующие строки съедаются как ответы.

`NO_COLOR` и не-TTY — без ANSI.

Язык интерфейса: русский в v1. JSON-поля `id` и ключи — английские.

## 12. Безопасность самой Defendra

- Один бинарник, без плагинов из `/tmp`.
- Не качает скрипты с GitHub при работе.
- `apt` только из уже настроенных репозиториев системы.
- Exclusive lock на protect/undo.
- Свои файлы не должны быть world-writable — это отдельная проверка watch.
- Релиз: checksum и подпись `.deb`.

## 13. Не делаем в v1

- Смена SSH-порта.
- Блокировка учётной записи root (`passwd -l root` и аналоги) — ломает консоль хостера.
- «Анти-DDoS» демоны, nft-наборы на 10 тысяч сетей, установка Cloudflare-агента.
- Автоматическое удаление пользователей и пакетов.
- CIS Level 2, SELinux, аудит всех syscall.
- Панель в браузере, аккаунт, облако.
- Debian/CentOS.
- Исправление по одному ID как главный UX (`defendra fix SSH-001`). Внутри protect идёт пайплайн шагов, не меню из 40 галок.
- Автоматический reboot.
- Генерация приватного SSH-ключа на сервере.
- Произвольное `defendra allow 8080`. Только `allow-site` (80 и 443).
- `git clone` / `go install` как основной способ установки.

## 14. Критерии приёмки v1

На пустой Ubuntu 24.04 в VM, вход root по паролю:

1. Без ключа `protect` ставит файрвол, fail2ban, обновления, **не** выключает пароль, печатает как добавить ключ, exit 1 (неполная защита).
2. С вставленным ключом повторный `protect` создаёт `admin`, выключает root и пароль **по SSH**, текущая сессия жива. Печатает ритуал второго окна («это окно пока НЕ закрывайте»).
3. С другой машины `ssh admin@ip` по ключу проходит, `ssh root@ip` с паролем — нет. Учётная запись root **не** заблокирована: `passwd -S root` не показывает `L`. С консоли (не SSH) root с паролем хостера входит.
4. Redis, слушавший `0.0.0.0:6379`, снаружи больше не открывается.
5. `defendra status` зелёный.
6. Повторный `protect` ничего вредоносного не делает.
7. `undo` с консоли возвращает предыдущий sshd (пароль SSH снова работает, если так было).
8. Выключение UFW руками → на следующий день MOTD жёлтый/красный, `protect` включает обратно.
9. Утилита не обращается никуда, кроме `apt` во время установки пакетов.
10. На сервере без веб-сервера 80/443 закрыты. `sudo defendra allow-site` открывает только 80 и 443, UFW остаётся active, SSH по-прежнему allowed. Повторный `allow-site` — no-op, exit 0.
11. Если nginx слушает 80, а allow-site не делали — status жёлтый с командой `allow-site`, не с `ufw disable`.
12. README описывает путь от письма хостера до protect, без Go. Две команды установки.
13. `defendra` без аргументов — русское меню, не usage cobra.
14. `defendra protect` без sudo — подсказка с `sudo`, не permission denied.
15. Вставка PRIVATE KEY — отказ, просят `.pub`.
16. В тексте protect нет слов UFW, fail2ban, sshd, jail (внутренние логи можно).
17. На экране конца закрытия SSH есть «ЭТО ОКНО НЕ ЗАКРЫВАЙТЕ» и таблица двух паролей.
18. `defendra help` содержит блок «не вхожу».
19. Ни один пользовательский экран не советует выключить файрвол.
20. Слушающий FastPanel/аналог — вопрос про порт; Enter оставляет доступ.

## 15. Этапы реализации

Делаем в этом порядке, каждый этап уже можно поставить на тестовый VDS.

**M0 — каркас.** Go-модуль, CLI, Ubuntu/root, `defendra` меню, `defendra help` заглушка FAQ, `version`. Без cobra-usage новичкам.

**M1 — факты.** Сбор: sshd, пользователи, ключи, порты, ufw, пакеты, fail2ban, панели. JSON-снимок. Ещё ничего не меняем.

**M2 — status + help.** Каталог ID, русские экраны из UX.md, `--format json` спрятан.

**M3 — protect без закрытия SSH.** Пользователь, пакеты, UFW, прогресс «шаг N из 9», панели, fail2ban, unattended-upgrades, sysctl, базы. Dry-run, backup, lock. `allow-site`. Валидация ключа.

**M4 — закрытие SSH.** Gates, drop-in, reload, ритуал, два пароля, MOTD, timer. Сценарий «пока без ключа». Root не lock.

**M5 — undo, идемпотентность, UX-приёмка §14.**

После v1, не раньше: профили «только БД», HTML, точечный explain+fix, Debian.
